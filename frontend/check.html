Open a new tab after async logic

Each button runs a simulated async task (a delay standing in for your API call), then opens the portal in a new tab. Try them in Safari and Chrome and compare.

1. Open blank tab first, navigate later recommended

The tab opens synchronously inside the click, so it counts as user-initiated. The URL is set once your logic finishes.

2. Prepare first, open on click most reliable

Step A does the async work ahead of time (on page load, hover, etc.). Step B opens the tab instantly in a synchronous click.

3. Await, then window.open often blocked

The naive version. Works in Chrome with short delays; Safari usually blocks it. A manual link appears if it is blocked.

Popup blocked: click here to open the portal

4. Spinner on this page, then auto-open or fall back to a link recommended for spinners

Shows a spinner here while the logic runs. When done, it checks navigator.userActivation.isActive. If the click is still valid, the tab opens automatically. If not, the button becomes a real link that always works.

Your portal is ready. Open portal

5. Same tab never blocked

Navigating the current tab after an await is not a popup, so no browser blocks it.

6. Prefetch on hover or focus, open instantly on click most common in production

Logic starts when the pointer enters or the button gets focus. If it is done by the click, the tab opens synchronously with no spinner. If not, it falls back to the blank-tab pattern. Hover the button, wait for the delay, then click.

7. Fire-and-forget logging, then open synchronously for analytics and audit

If the logic is only tracking, send it with fetch keepalive (or sendBeacon) and open the tab in the same click. Nothing is awaited.

8. Native anchor with ping no JavaScript on click

A real link with target="_blank" is never treated as a popup. The browser sends the ping request in the background. Chrome and Safari support it; Firefox disables it by default. Needs a real endpoint to receive the ping.

Open portal

9. Interstitial page opened on click used by payment and OAuth flows

The click synchronously opens a loading page that you control (here a blob URL; in production, a route like /redirecting). That page runs the logic with its own spinner, then redirects. Unlike pattern 1, the new tab shows branded content and does its own work.

10. Server-side redirect needs a backend

Not runnable in a static file. Point an anchor at your own endpoint, run the logic on the server, and answer with a redirect. The browser performs the navigation, so nothing is blocked, including in in-app browsers.

<a href="/go/portal" target="_blank" rel="noopener">Open portal</a>

// Express
app.get("/go/portal", async (req, res) => {
  await audit(req.user);               // your logic
  res.redirect(302, await buildUrl()); // external portal
});

11. Toast first, then open the tab toast shown before leaving the page

A toast with a spinner appears on this page while the logic runs. It stays visible for at least the time below so users can read it. Then the tab opens. If the browser no longer allows an automatic open, the toast turns into an "Open portal" link. Keep the minimum short: in Safari a long wait uses up the click's permission.
